## 一、问题回顾：为什么固定 RANK 列不够好？

在 V7/V8 的实验中，我们把权重矩阵的**固定若干列**（tail 或 head）用 INT8 量化，其余用 INT4。实验结果：

| 配置 | PPL (Anone) | 距 FP16 |
|------|-------------|---------|
| FP16 baseline | 10.04 | — |
| GPTQ 4bit (raw) | 10.38 | +0.34 |
| **smooth_ta_r16 (V7 最佳)** | **10.34** | **+0.30** |
| smooth_ta_r128 (V7) | 10.42 | +0.38 |

**关键发现**：r16 和 r128 差距只有 0.08，说明多给 INT8 列并没有显著帮助。

**根本原因**：Outlier（离群值）在权重矩阵中不是均匀分布在某些列上的，而是**散落在不同的行列交叉位置**。固定列的 INT8 补偿是"一刀切"的，很多 INT8 预算浪费在了不需要的位置。

## 二、新方案：子矩阵级混合精度

### 核心思想

把权重矩阵切成一个个小方块（子矩阵），比如 128×128 的块。然后：

1. **评估每个块的量化敏感度**（哪些块量化误差大）
2. **选出最敏感的 5% 的块**，用 INT8 量化
3. **其余 95% 的块**，用 INT4 量化

这样，INT8 的预算精准地花在了最需要的地方。

### 直观图示

```
原始权重矩阵 W (2560 × 2560)，切成 128×128 的块 → 20×20 = 400 个块

┌────┬────┬────┬────┬────┬─···─┬────┐
│ 4b │ 4b │ 4b │ 8b │ 4b │     │ 4b │  ← 8b 表示该块用 INT8
├────┼────┼────┼────┼────┼─···─┼────┤
│ 4b │ 4b │ 4b │ 4b │ 4b │     │ 4b │
├────┼────┼────┼────┼────┼─···─┼────┤
│ 4b │ 8b │ 4b │ 4b │ 4b │     │ 4b │
├────┼────┼────┼────┼────┼─···─┼────┤
│ 4b │ 4b │ 4b │ 4b │ 8b │     │ 4b │
├────┼────┼────┼────┼────┼─···─┼────┤
│    │    │    │    │    │     │    │
⋮    ⋮    ⋮    ⋮    ⋮    ⋮     ⋮    ⋮
├────┼────┼────┼────┼────┼─···─┼────┤
│ 4b │ 4b │ 8b │ 4b │ 4b │     │ 4b │

400 个块中，选 20 个（5%）用 INT8，其余 380 个用 INT4
```

### 与 V7 的对比

| 维度 | V7 Tail Absorb | V9 子矩阵混合精度 |
|------|---------------|------------------|
| 高精度区域粒度 | **整列** | **子矩阵块** |
| 高精度区域选择 | 固定位置（tail/head） | **自适应**（按敏感度选择） |
| 能否覆盖散落的 outlier | ❌ 只能覆盖特定列 | ✅ 可以覆盖任意位置 |
| 额外存储开销 | tail_rank × d_out × (8-4)/8 | 5% × d_out × d_in × (8-4)/8 |
| 推理计算方式 | 单次矩阵乘 | 密集 INT4 乘 + 稀疏修正乘 |

## 三、你提出的三个关键问题

### 问题 1：怎么低代价地找到最佳的 5% 子矩阵位置？

#### 直觉验证：是不是就是 Outlier 所在的子矩阵？

**基本正确，但需要更精确的度量。** 单纯看 outlier 数量不够，因为：
- 一个块里有 1 个超大 outlier vs 10 个中等 outlier，后者的总量化误差可能更大
- 有些块虽然没有极端 outlier，但整体分布不适合 INT4（比如双峰分布）

#### 推荐方案：量化误差评分法（代价低，效果好）

```
对每个子矩阵块：
  1. 做一次 INT4 fake-quant（量化再反量化）
  2. 计算量化误差的 Frobenius 范数
  3. 误差最大的 5% 块 → 标记为 INT8
```

**代价分析**：
- 只需要一次全矩阵的 INT4 量化模拟（非常快，纯张量运算）
- 不需要额外的校准数据
- 不需要 Hessian 信息（虽然用 Hessian 可以更精确，但代价更高）

#### 备选方案对比

| 方案 | 代价 | 精度 | 说明 |
|------|------|------|------|
| A. 权重范数 | ⭐ 最低 | ⭐⭐ | 只看权重绝对值大小，不考虑量化特性 |
| **B. 量化误差** | **⭐⭐ 低** | **⭐⭐⭐ 好** | **推荐起步方案** |
| C. Hessian 加权误差 | ⭐⭐⭐ 中等 | ⭐⭐⭐⭐ 最好 | 需要 Hessian 对角线，但 GPTQ 本身就会算 |

**建议**：先用方案 B 跑通流程，如果效果不够好再升级到方案 C。方案 C 的 Hessian 对角线在 GPTQ 流程中本来就会计算，所以实际额外代价不大。

### 问题 2：结合 per-block 量化策略，怎么量化？哪些共用一个 scale？

#### 现有的 scale 机制回顾

当前 GPTQ 使用 **per-group scale**：
- `groupsize = 128`（沿 input 维度每 128 列共享一个 scale）
- 每行有 `d_in / 128` 个 scale 值
- Scale shape: `(d_out, d_in // groupsize)`

#### V9 的 scale 策略

**INT4 块（95%）**：完全复用现有 GPTQ 的 per-group scale，不做任何改变。

**INT8 块（5%）**：每个子矩阵块一个独立的 symmetric scale。
```
scale_int8 = max(|block|) / 127
```

**为什么这样设计？**
- INT4 部分与标准 GPTQ 完全兼容，不引入额外复杂度
- INT8 块数量少（只有 5%），每块一个 scale 的存储开销可以忽略
- 子矩阵块内部的值分布相对集中，一个 scale 足够

#### 关键约束：block 尺寸与 groupsize 对齐

```
推荐：bcol = groupsize = 128

这样每个子矩阵块的列范围恰好对应一个 GPTQ group，
INT4 块的 scale 就是标准 GPTQ group scale，无需特殊处理。
```

如果 `bcol ≠ groupsize`，需要处理一个块跨越多个 group 的情况，增加复杂度。**强烈建议 bcol = groupsize**。

#### Scale 存储总结

| 组件 | Shape | 说明 |
|------|-------|------|
| INT4 group scale | (d_out, d_in // 128) | 与标准 GPTQ 完全相同 |
| INT4 group zero | (d_out, d_in // 128) | 与标准 GPTQ 完全相同 |
| INT8 block scale | (N_high,) 或 (N_high, brow) | 每块一个或每块每行一个 |
| Block mask | (nrow, ncol) bool | 标记哪些块是 INT8 |

### 问题 3：推理时的稀疏矩阵乘开销大吗？可以实现吗？

#### 计算分解

推理时的矩阵乘被分解为两步：

```
Y = W @ X
  = W_int4_full @ X      ← 标准密集 INT4 矩阵乘（100% 计算量）
  + W_correction @ X      ← 稀疏修正矩阵乘（~5% 计算量）
```

其中：
- `W_int4_full`：**所有**元素都用 INT4 量化的完整矩阵
- `W_correction`：只在 INT8 块位置有非零值的稀疏矩阵
  - `W_correction[block] = dequant_int8(block) - dequant_int4(block)`
  - 即 INT8 量化结果与 INT4 量化结果的**差值**

#### 开销分析

| 组件 | 计算量 | 说明 |
|------|--------|------|
| 密集 INT4 GEMM | 100% | 与纯 INT4 方案相同，可用现有 INT4 kernel |
| 稀疏修正 GEMM | ~5% | 只有 5% 的块参与计算 |
| **总计** | **~105%** | **额外开销约 5%** |

#### 实现可行性

**方案 A：PyTorch Block Sparse Tensor（最简单）**

PyTorch 2.0+ 支持 BSR（Block Sparse Row）格式：
```python
sparse_correction = torch.sparse_bsr_tensor(
    crow_indices, col_indices, values,
    size=(d_out, d_in)
)
Y_correction = torch.sparse.mm(sparse_correction, X)
```
- ✅ 原生支持，无需自定义 kernel
- ⚠️ 性能可能不是最优（通用稀疏 kernel 的 overhead）

**方案 B：手动 Gather-Scatter（中等复杂度）**

```python
# 只对 INT8 块涉及的列做 gather
# 执行小规模密集 GEMM
# scatter-add 到输出
```
- ✅ 可以利用密集 GEMM 的高效实现
- ⚠️ 需要手动管理索引

**方案 C：Triton/CUTLASS 自定义 Kernel（最高性能）**

- ✅ 可以做到接近理论最优
- ⚠️ 开发成本高

#### 实际建议

1. **原型阶段**：用方案 A（PyTorch BSR）或直接用 for 循环遍历 INT8 块，验证精度
2. **性能优化阶段**：如果 5% 的开销在实际推理中可接受，就不需要优化
3. **极致优化**：用 Triton 写一个 fused block-sparse GEMM kernel

**关键判断**：对于 Qwen3-4B 这个规模的模型，5% 的额外计算开销在实际推理中几乎不可感知（latency 增加 < 5%，因为推理通常是 memory-bound 而非 compute-bound）。

## 四、与 GPTQ 误差传播的兼容性

这是一个**关键的技术细节**。GPTQ 是逐列处理的，每一列量化后的误差会传播到右边所有列。

### 问题：子矩阵级混合精度如何与 GPTQ 的逐列处理兼容？

**答案**：在 GPTQ 的逐列循环中，对每一列的不同行段（row segment）使用不同的量化精度。

```
处理第 col 列时：
  对于行段 [0:128]   → 查 mask → 如果该块是 INT8，用 INT8 量化
  对于行段 [128:256] → 查 mask → 如果该块是 INT4，用 INT4 量化
  对于行段 [256:384] → 查 mask → ...
  
  误差传播：整列的误差统一传播到右边（与标准 GPTQ 完全相同）
```

**关键点**：
- 量化精度的决策是 **block-level** 的
- 误差传播仍然是 **full-matrix** 的（不是 block-local 的）
- GPTQ 的 Hessian 补偿链保持完整

这与 V7 Tail Absorb 的思路一致：V7 是按列决定 INT4/INT8，V9 是按（行段, 列）决定。误差传播机制不变。

## 五、act-order 排列与子矩阵的交互

### 问题

当 `actorder=True` 时，GPTQ 会按 Hessian 对角线对列重新排序。这会改变哪些列落在哪个子矩阵块中。

### 建议

1. **先做 act-order 排列**
2. **在排列后的矩阵上计算子矩阵敏感度**
3. **在排列后的矩阵上执行 GPTQ + 混合精度量化**
4. **量化完成后用 invperm 还原列顺序**
5. **同时还原 block mask 的列索引**

这样 block 选择与 GPTQ 的处理顺序一致。

## 六、预期效果与风险

### 预期收益

| 指标 | 预期 | 理由 |
|------|------|------|
| PPL (Anone) | < 10.34 (V7 最佳) | INT8 预算精准投放到高误差区域 |
| PPL (A4g128) | < 13.13 (V7 最佳) | 同上 |
| 额外推理延迟 | < 5% | 稀疏修正计算量小 |
| 额外存储 | ~5% × (8-4)/4 = ~5% | 只有 5% 的块需要额外 4bit |

### 风险点

| 风险 | 严重度 | 缓解措施 |
|------|--------|----------|
| Block 粒度太粗，无法精确覆盖 outlier | 中 | 尝试更小的 block size (64×64) |
| 稀疏修正 GEMM 实际性能差 | 低 | 5% 的稀疏度很低，PyTorch BSR 应该够用 |
| GPTQ 误差传播与 block 混合精度冲突 | 低 | V7 已验证列级混合精度与误差传播兼容 |
| 敏感度评分不准确 | 中 | 提供多种 metric 选择，可消融对比 |

## 八、待讨论的问题

1. **Block 尺寸**：128×128 是否合适？更小的块（如 64×64）能更精确地覆盖 outlier，但块数量增加 4 倍，选择和管理更复杂。

2. **Budget 比例**：5% 是否合适？需要在精度收益和推理开销之间权衡。

3. **是否需要 per-layer 自适应 budget**：有些层的 outlier 更多，是否应该给更多 INT8 预算？还是全局统一 5%？

4. **与 SmoothQuant 的交互**：SmoothQuant 已经平滑了部分 outlier，子矩阵混合精度是否还有足够的收益？需要实验验证。

5. **是否考虑 INT6 等中间精度**：除了 INT4/INT8 二选一，是否考虑更细粒度的精度分配？（复杂度会显著增加）

6. **量化顺序**：是先选块再 GPTQ，还是 GPTQ 过程中动态调整？当前方案是前者（先选块），因为更简单。
